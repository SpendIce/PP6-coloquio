HTTP y contrato

Cada código de estado y cada header tiene un porqué. Si lo sabés, «buenas prácticas REST» deja de ser una frase.

Al terminar vas a poder: defender cada código de estado y cada header de la API citando la norma (RFC 9110) o un acuerdo con el profe.

1. Contrato primero C

La consigna (§3.2) pide definir «contratos de la API REST (OpenAPI/Swagger) … antes de la generación de código». Eso es openapi.yaml: se escribió antes del código, y el código lo cumple. Si te piden «el Swagger», es ese archivo. No hay Swagger UI levantada (no está springdoc), pero el YAML se puede pegar en editor.swagger.io para verlo.

2. Crear: POST /api/links

POST /api/links            {"destination": "https://…"}
← 201 Created              {shortUrl, alias, expiresAt, reuseNotice}   Cache-Control: no-store
← 400 Bad Request          {error: "OWN_ORIGIN", message: "La URL … pertenece al propio acortador."}
  • POST + sustantivo (/api/links): crear un recurso en una colección.
  • 201 y no 200: la norma dice que 201 significa «se crearon uno o más recursos nuevos» (RFC 9110 §15.3.2), y acá se creó una asignación. Detalle que te pueden marcar: no se manda header Location. La norma lo permite (sin Location, el recurso es la URI pedida), y el enlace creado viaja en shortUrl.
  • POST no es idempotente: repetirlo crea otra asignación, y eso es lo acordado (Q2, Q21).
  • 400 con {error, message}: error es un código estable que lee una máquina (la extensión lo muestra), y message es para la persona (la web lo muestra tal cual). Los códigos posibles están enumerados en el contrato: EMPTY_DESTINATION, DESTINATION_TOO_LONG, MALFORMED_DESTINATION, UNSUPPORTED_SCHEME, OWN_ORIGIN e INVALID_REQUEST.
  • Campos desconocidos → 400: el contrato declara additionalProperties: false y Jackson tiene fail_on_unknown_properties: true. Un cliente que manda basura se entera en vez de ser ignorado en silencio.

¿Quién convierte la excepción en 400? ApiExceptionHandler (@RestControllerAdvice): un solo lugar para todos los errores. El controlador queda en tres líneas. Y la respuesta es un DTO (LinkCreatedResponse), nunca la entidad JPA: si mañana cambia la tabla, el contrato no se rompe ADR 0001.

3. Resolver: GET /{alias} C

GET /7      ← 302 Found       Location: https://destino…   Cache-Control: no-store
GET /zz     ← 404 Not Found   página «Este enlace no existe o venció»   Cache-Control: no-store

¿Por qué 302 y no 301?

301 significa «se mudó para siempre» (§15.4.2), y los navegadores lo cachean por defecto. Cuando el alias 7 se recicle, el navegador de alguien seguiría mandándolo al destino viejo sin consultar al servidor: no podrías ni vencerlo ni reasignarlo. 302 dice «está temporalmente en otro lado, seguí usando la URI original» (§15.4.3), que es exactamente un enlace que vence.

¿Y no-store?

Refuerza lo mismo: le prohíbe a cualquier caché (navegador, proxy) guardar la respuesta (RFC 9111). Tampoco se cachea el 404, porque ese alias puede volver a estar vigente en un minuto.

¿Por qué 404 y no 410 Gone?

410 significa «se fue y no vuelve». Un alias vencido sí vuelve, porque se recicla. Además, Q11 acordó la misma respuesta para «nunca existió» y «venció», y eso tiene otra ventaja: no revela qué alias existieron.

¿Cómo no choca /{alias} con /app.js o /api/links?

El mapeo es @GetMapping("/{alias:[1-9A-HJ-NP-Za-km-z]{1,32}}"). Un punto (app.js) o una barra (/api/links) no calzan con el patrón, así que esas rutas nunca entran como alias. Y los códigos api y error se reservan para que el generador no los emita (lección 2).

4. ¿Es «REST» de verdad?

Respuesta honesta: es una API HTTP orientada a recursos, con verbos y códigos de estado bien usados. Es el nivel 2 del modelo de madurez de Richardson. No tiene hipermedia (HATEOAS, nivel 3). Para dos operaciones es razonable; decirlo con nombre y apellido suma más que afirmar «es RESTful».

5. Practicá

¿Por qué la redirección es 302 y no 301?

✘ Las extensiones ni siquiera resuelven enlaces: solo crean.

✘ La velocidad es la misma; la diferencia está en el significado y en la caché.

✔ Un 301 cacheado sobrevive al vencimiento y a la reasignación del alias.

Mandan {"destination": "https://x.com", "alias": "hola"}. ¿Qué responde?

✔ Propiedad desconocida: additionalProperties: false en el contrato y fail_on_unknown_properties en Jackson. Lo prueba rechazaPropiedadesDesconocidasDelContrato.

✘ Ignorar en silencio es lo que se evitó a propósito: el cliente creería que pidió un alias.

✘ Los alias personalizados no existen en la etapa 1. Están analizados en evidencia-evolucion.md, sin implementar.

¿Quién transforma InvalidDestinationException en un 400?

✘ El controlador no tiene ningún try/catch: la excepción lo atraviesa.

✔ @RestControllerAdvice + @ExceptionHandler: usa el reason como error y el mensaje como message.

✘ El validador es dominio: lanza la excepción, pero no sabe que existe HTTP.

¿Por qué no se devuelve directamente AssignmentEntity como JSON?

✔ Cambiar una columna rompería la web y las extensiones. El DTO desacopla (ADR 0001).

✘ Técnicamente puede serializarlas. El problema es de diseño, no de capacidad.

✘ No es una cuestión de rendimiento.

En voz alta: «Justifiquen los códigos de estado de su API.»

Respuesta modelo

«Crear es un POST a la colección /api/links y responde 201 porque crea una asignación. No es idempotente, y eso lo acordamos: cada pedido es una asignación nueva. Si la entrada es inválida respondemos 400 con un código estable y un mensaje legible, todo centralizado en un ControllerAdvice. Resolver responde 302, no 301, porque el 301 se cachea como permanente, y nuestro alias vence y se reasigna. Por lo mismo, todo va con no-store. Si no hay asignación vigente, respondemos 404 y no 410, porque el alias puede volver a usarse, y además así no revelamos si existió. El contrato está en openapi.yaml y se escribió antes del código.»
